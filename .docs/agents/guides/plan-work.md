# Planning work

A good task makes the implementation bounded and reviewable.

Define:

- the proven problem and why it matters;
- current evidence and affected users;
- scope and non-goals;
- owning component and subsystem;
- dependencies and conflicts;
- allowed and forbidden paths;
- governing architecture documents;
- expected behavior and compatibility impact;
- acceptance criteria;
- exact validation commands;
- documentation and release impact;
- rollback or safe-failure considerations.

Separate architecture decisions from implementation tasks. A task must not hide an unresolved semantic or package-boundary decision.
