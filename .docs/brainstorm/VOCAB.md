Understood. **Everything previously proposed about selection vocabulary, keywords, query syntax, template variables, providers, imports, exports, and barrels is now treated as unapproved.**

You will make the decisions. I will only:

* propose options;
* explain trade-offs;
* test understandability with examples;
* identify risks and contradictions;
* record exactly what you approve, reject, or defer;
* avoid silently extending an approved decision.

## Decision statuses

We will use only these statuses:

```text
UNREVIEWED
PROPOSED
UNDER REVIEW
APPROVED
REJECTED
DEFERRED
```

I will never mark something `APPROVED` unless you explicitly approve it.

## Review order

### 1. Core selection sentence

Decide how a pack author expresses:

```text
What is selected?
How is it filtered?
How many template invocations are created?
```

Status: **UNREVIEWED**

### 2. Selection target vocabulary

Possible concepts to evaluate individually:

```text
package
module
group
property
schema
field
operation
policy
event
storage mapping
value source
view
presentation
workflow
workflow step
```

Questions:

* Which deserve direct selection?
* Which should only appear as variables under another selection?
* Should names be singular or plural?
* Should target names exactly match Runtime IR terms?

Status: **UNREVIEWED**

### 3. Invocation/cardinality vocabulary

We must choose understandable words for:

* exactly one selected item;
* one invocation per item;
* one invocation receiving all items;
* one invocation per grouping.

No previous terms such as `one`, `each`, `all`, `collect`, `groupBy`, `grouped`, or others are approved.

Status: **UNREVIEWED**

### 4. Filter and query design

We must decide:

* whether filters use nested YAML, concise expressions, or another structure;
* supported logical operators;
* how users filter fields, schemas, operations, facets, tags, capabilities, and relationships;
* how much traversal is safe;
* what must remain deliberately unsupported.

Status: **UNREVIEWED**

### 5. Grouping and ordering

We must decide:

* grouping vocabulary;
* allowed grouping values;
* default ordering;
* explicit ordering syntax;
* whether custom grouping is allowed;
* how deterministic ordering is guaranteed.

Status: **UNREVIEWED**

### 6. Template variable vocabulary

For every approved selection, we must document:

* primary selected variable;
* collection variable;
* owner variables;
* related semantic variables;
* universal template variables;
* optional deeper context.

Example questions:

* Does selecting schemas expose `schema` or `item`?
* Are `package`, `module`, and `group` always available?
* Should a collection be called `schemas`, `items`, or `selection`?
* How does a template discover available variables?

Status: **UNREVIEWED**

### 7. Relationship access

We must decide how templates access related meaning:

```text
schema → fields
operation → input/output schemas
schema → operations using it
workflow → steps
view → operations
```

Questions:

* Which relationships are direct variables?
* Which require explicit context requests?
* Which may be used in selection filters?
* How do we avoid arbitrary graph traversal?

Status: **UNREVIEWED**

### 8. Template-to-template dependencies

We must separately define vocabulary for:

* including another template or fragment;
* importing a symbol generated by another template;
* depending on another generated artifact;
* requiring another artifact to exist first.

Status: **UNREVIEWED**

### 9. Providers and generated symbols

We must decide:

* how a template declares what it generates;
* how generated symbols are identified;
* how several representations of one schema are distinguished;
* how another template requests the correct symbol;
* how ambiguity is handled.

No previous vocabulary such as `provides`, `role`, `subject`, or `variant` is approved.

Status: **UNREVIEWED**

### 10. Imports

We must decide how users express:

```text
This generated template needs a symbol produced by that template.
```

The design must explain:

* semantic identity;
* source template;
* imported symbol;
* relative, aliased, package, or barrel paths;
* multiple imported symbols;
* cross-language errors;
* project-provided static imports.

Status: **UNREVIEWED**

### 11. Exports and barrels

We must decide how a barrel template says:

```text
Export emissions created by these templates.
```

Questions:

* Does a barrel reference templates, artifacts, symbols, or selections?
* How does it restrict exports to the current module or group?
* How are names and paths exposed to the barrel template?
* Can it export project bindings and external symbols?

Status: **UNREVIEWED**

### 12. Emission vocabulary

We must choose clear meanings for terms such as:

```text
template
template invocation
emission
artifact
output
generated file
provided symbol
```

Each term must have one meaning across packs, diagnostics, plans, and CLI output.

Status: **UNREVIEWED**

### 13. Conditions and empty selections

We must decide:

* whether templates run when nothing is selected;
* whether empty collections render or skip;
* how exactly-one selections behave with zero or several matches;
* how conditional templates are expressed.

Status: **UNREVIEWED**

### 14. Explainability vocabulary

Every decision must support understandable explanations:

```text
Why was this selected?
Why was it skipped?
What variables were supplied?
What did this template generate?
Why was this import created?
Which template provided this symbol?
```

Status: **UNREVIEWED**

### 15. Scalability constraints

Selection design must remain compatible with:

* large packages;
* module-based loading;
* bounded memory;
* concurrent planning and rendering;
* deterministic ordering;
* planning before output mutation.

These constraints may reject otherwise convenient syntax, but they do not decide user-facing vocabulary by themselves.

Status: **UNREVIEWED**
