# Template and pack file model

## One descriptor per source file

Every non-ignored file under a pack content root becomes exactly one immutable `PackFileDescriptor`.

Automatic discovery creates the descriptor. `filePatterns` and exact `files` entries refine that same descriptor; they never create a second emission for the same source file.

## Source path owns the default destination

The content-root-relative source path is the default destination program.

```text
templates/{repositories}/[entity.name.kebab.s].repository.ts.jinja
```

After resolving `{repositories}` and `[entity.name.kebab.s]`, and stripping only `.jinja`, the output may be:

```text
src/repositories/order.repository.ts
```

The IR entity does not expose `fileName`. Literal filename text and target suffixes come from the authored source path. Dynamic portions come from typed path expressions.

See [`00-path-expressions-and-name-tokens.md`](00-path-expressions-and-name-tokens.md).

## Roles

### Template

A file with a recognized template-engine suffix that renders to one or more predeclared outputs.

### Barrel

An authored template receiving planned exports and dependencies. It uses the same path composition rules as every other template and is not generated by a special root barrel subsystem.

### Static

A text file copied without rendering. Static files are emitted by default when no template-engine suffix is recognized.

### Binary

A binary file copied byte-for-byte.

### Partial

A template source available to compatible templates but never directly emitted.

### Documentation

Pack authoring and setup documentation. It is not emitted unless intentionally placed below an emitting content root and configured accordingly.

## Engine and target inference

For:

```text
user.entity.ts.jinja
```

- `.jinja` resolves the template-engine adapter;
- `.ts` resolves the target-syntax adapter;
- the output suffix remains `.ts`;
- the `.jinja` suffix is removed after output planning.

Inference uses longest-known suffix matching. Explicit target or engine declarations are allowed only for ambiguous filenames such as `Dockerfile.jinja` or for documented aliases. A contradictory explicit declaration is rejected.

## Path-token parsing is independent from engine parsing

The path planner parses `{recipe}`, `[expression]`, and escaping tokens before the template engine renders content. Jinja never plans its own filename and cannot emit hidden destinations.

A template-engine adapter receives an already planned file context.

## Exact file configuration

An exact `files` entry configures an existing source descriptor:

```yaml
files:
  "{repositories}/[entity.name.kebab.s].repository.ts.jinja":
    id: repository
    role: template
    selection:
      use: entities
    uses:
      bindings: [baseRepository]
    provides:
      - repository.entity
```

No `output.path` is required because the authored source path already expresses it.

Typical exact-file fields include:

- stable ID;
- role;
- selection when not introduced by a path recipe;
- binding usage;
- includes;
- providers and requirements;
- local target and engine rule patches;
- conditions;
- lifecycle;
- profile membership;
- authored barrel export requirements;
- exceptional explicit output override;
- multiple predeclared named outputs.

## Explicit output overrides

An explicit output override is allowed when source-tree placement cannot represent the destination cleanly. It uses the same typed path grammar:

```yaml
output:
  parts:
    - gen
    - "[project.name.kebab.o]-client.ts"
```

It must not use Jinja, arbitrary Python values, hidden runtime fields, or invented semantic properties.

## Multiple outputs

A template may produce multiple named outputs only when all output IDs and path expressions are declared in `CodepotgPack.yaml` before rendering.

The engine may support named output blocks, but it cannot invent output paths or output IDs dynamically.

## Authored barrels

A barrel template may contain comments, headers, custom text, side-effect imports, exports, or framework-specific syntax.

The planner supplies immutable export data containing:

- member artifact ID;
- exported symbols;
- source and destination module paths;
- target syntax;
- deterministic ordering;
- dependency and lifecycle data.

The target-language adapter resolves export/module syntax. The authored barrel template decides the final content.

## Static and binary files

Static and binary source paths are expanded through the same recipe/token system as templates:

```text
{projectRoot}/.gitignore
{package}/assets/logo.png
{resource}/README.md
```

Static text is copied unchanged. Binary bytes are copied unchanged. A selection-bearing recipe may fan either one out across resources, modules, packages, or other selected records.

## Partials and target compatibility

A partial declares a target or neutral status.

- TypeScript templates may include TypeScript and neutral partials;
- Dart templates may include Dart and neutral partials;
- incompatible cross-target inclusion is rejected before rendering.

Partial paths are resolved through the pack template registry rather than arbitrary filesystem access.

## Duplicate destination policy

Two descriptors or invocations that plan the same destination are an error unless an explicit composition mechanism owns that destination. Last-write-wins behavior is prohibited.

Automatic discovery, path recipes, patterns, and exact file settings must still resolve to one source descriptor and one set of planned invocations.

## Tests

Required tests cover:

- one descriptor per source file;
- engine and target inference;
- source-path output derivation;
- name-case and plurality tokens;
- ambiguous explicit declarations;
- static text and binary copying;
- authored barrel contexts;
- partial target compatibility;
- multiple declared outputs;
- duplicate output rejection;
- path safety and deterministic ordering;
- rejection of `entity.fileName`, `module.directory`, and other undeclared convenience values.
