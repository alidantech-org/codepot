# Template and pack file model

## One descriptor per source file

Every non-ignored file under a pack content root becomes exactly one `PackFileDescriptor`.

Automatic discovery creates the descriptor. `filePatterns` and exact `files` entries refine the same descriptor; they do not add duplicate emissions.

## Roles

### Template

A file with a recognized template-engine suffix that renders to one or more declared outputs.

### Barrel

An authored template receiving planned exports and dependencies. It is not generated by a special root barrel subsystem.

### Static

A text file copied without rendering. Static files are emitted by default when no template-engine suffix is recognized.

### Binary

A binary file copied byte-for-byte.

### Partial

A template source available to compatible templates but never directly emitted.

### Documentation

Pack authoring/setup documentation. It is not emitted unless explicitly configured as generated content.

## Engine and target inference

For `user.entity.ts.jinja`:

- `.jinja` resolves the template-engine adapter;
- `.ts` resolves the target syntax adapter;
- output suffix remains `.ts`.

Inference uses longest-known suffix matching. Explicit target or engine declarations are allowed only for ambiguous filenames or supported aliases.

An explicit declaration that contradicts a recognized filename target is an error unless a documented opt-out is approved.

## Output expressions

Output paths are planned from typed path expressions, not arbitrary access to the full template engine.

Supported values may include:

- literal segments;
- selected record fields;
- safe naming transforms;
- pack options;
- declared binding/package values;
- group keys;
- named output IDs.

Every path is validated for traversal, invalid platform segments, collisions, determinism, and allowed output roots before rendering.

## Multiple outputs

A template may produce multiple named outputs only when all outputs are declared in the manifest before rendering.

The engine may implement named output blocks, but templates cannot invent paths or output IDs dynamically.

## Authored barrels

A barrel template may contain comments, headers, custom text, side-effect imports, exports, or framework-specific syntax.

The planner supplies an immutable export context containing:

- member artifact ID;
- symbol names;
- source and destination module path;
- target syntax;
- ordering/dependency information;
- lifecycle state.

The target-language adapter resolves paths and export syntax. The template decides final authored layout.

## Static files

Static files are copied by default because packs may be complete project assets. Examples:

```text
.gitignore
.env.example
LICENSE
Makefile
Dockerfile
images
fixture data
editor settings
```

A static file may be copied once or fanned out through a selection/folder pattern. Only its destination changes; its content is not rendered.

## Partials and compatibility

A partial declares a target or neutral status.

- a TypeScript template may include TypeScript and neutral partials;
- a Dart template may include Dart and neutral partials;
- cross-target inclusion is rejected before rendering.

## Duplicate output policy

Two descriptors that plan the same destination are an error unless an explicit composition mechanism owns that destination. Last-write-wins behavior is prohibited.

## Raw files and template suffixes

A file with a recognized engine suffix is a template unless explicitly configured as a non-emitting partial. A static file is never rendered merely because its content contains template-like text.

## Tests

Required tests cover:

- one descriptor per source file;
- engine and target inference;
- ambiguous explicit declarations;
- static text and binary copying;
- authored barrel contexts;
- partial target compatibility;
- multiple declared outputs;
- duplicate output rejection;
- path safety and deterministic ordering.
